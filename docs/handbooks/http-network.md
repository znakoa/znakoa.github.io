### 一、 HTTP 基础体系与状态码

#### 1. 核心特征

- **灵活可扩展**：语法层面仅约定基础格式（空格分隔单词、换行分隔字段）；传输形式不仅支持文本，还支持图片、音频、视频等二进制数据。
- **请求-应答模式**：通常是一方发送请求，另一方接收并做出相应反馈。
- **可靠传输**：底层依赖 TCP/IP 协议栈，继承了其可靠传输与重传机制。
- **无状态 (Stateless)**：
  - **定义**：协议本身对事务处理没有记忆能力，同一 URL 的多次请求之间不存在上下文关联。
  - **“状态”的本质**：指客户端与服务器在某次会话中产生的数据。无状态意味着服务端默认不保留这些会话数据。
  - **实现有状态**：在应用层通过 Cookie 与 Session 机制补全会话状态；服务器对业务数据的持久化存储（如修改数据库）属于会话结果保存，不等于协议本身具备状态。

#### 2. HTTP 状态码体系

- **1xx（信息性状态码）**：
  - `101 Switching Protocols`：协议切换，常用于 HTTP 升级为 WebSocket。
- **2xx（成功状态码）**：
  - `200 OK`：服务器成功处理请求。
  - `204 No Content`：请求处理成功，但响应报文不包含实体的主体部分。
  - `206 Partial Content`：范围请求成功，常用于断点续传或音视频分段播放。
- **3xx（重定向状态码）**：
  - `301 Moved Permanently`：永久重定向，请求资源已永久分配新 URI。
  - `302 Found`：临时重定向，通常被实现为重定向到 GET 请求，不能确保 POST 仍保持 POST。
  - `303 See Other`：明确要求客户端使用 GET 请求重定向获取资源。
  - `304 Not Modified`：协商缓存命中，客户端本地缓存未失效，直接使用本地缓存。
  - `307 Temporary Redirect`：临时重定向，严格遵守规范，不允许将原始请求方法（如 POST）变更为 GET。
- **4xx（客户端错误状态码）**：
  - `400 Bad Request`：客户端请求报文存在语法错误或参数不合法。
  - `401 Unauthorized`：未认证，需要登录认证。
  - `403 Forbidden`：已认证但无权限访问该资源。
  - `404 Not Found`：服务器上无法找到请求的资源。
  - `405 Method Not Allowed`：服务器禁用了该请求使用的 HTTP 方法。
- **5xx（服务端错误状态码）**：
  - `500 Internal Server Error`：服务器内部错误，无法完成请求。
  - `502 Bad Gateway`：网关或代理服务器从上游服务器收到了无效响应。
  - `503 Service Unavailable`：服务器超载或停机维护，暂时无法提供服务。
  - `504 Gateway Timeout`：网关或代理服务器未能在规定时间内收到上游服务器的响应。

### 二、 网络分层模型与报文结构

#### 1. OSI 七层与 TCP/IP 四层映射

Plaintext

```
[OSI 七层模型]                    [TCP/IP 四层模型]
7. 应用层 (Application)   ──┐
6. 表示层 (Presentation)  ──┼──>  应用层 (HTTP, SSH, FTP, DNS)
5. 会话层 (Session)       ──┘
4. 传输层 (Transport)     ────>  传输层 (TCP, UDP)  ── [端口到端口]
3. 网络层 (Network)       ────>  网际层 (IP)        ── [主机到主机]
2. 数据链路层 (Data Link) ────>  网络接口层 (以太网) ── [MAC 地址]
1. 物理层 (Physical)      ──┘
```

> **四层与七层快速判别法则**：凡是由操作系统内核负责处理的通常属于四层及以下；凡是由应用程序（开发者代码）负责处理的通常属于七层。

#### 2. URI / URL 组成规范

标准格式：`scheme://host:port/path?query`



- **scheme**：方案名/协议名（如 `http`、`https`）。
- **host:port**：资源所在的主机名（域名或 IP）与端口号（HTTP 默认 80，HTTPS 默认 443）。
- **path**：资源在服务器上的抽象路径。
- **query**：查询字符串，以键值对表示附加筛选条件。
- **编码机制**：URI 规定特殊字符（`@`、`&`、`/` 等）及非 ASCII 字符（如中文）必须进行百分比编码（URL Encoding）。

#### 3. 报文结构规范

- **起始行 (Start Line)**：
  - 请求报文：`Method + Request-URI + HTTP-Version`（如 `GET /index.html HTTP/1.1`）。
  - 响应报文：`HTTP-Version + Status-Code + Reason-Phrase`（如 `HTTP/1.1 200 OK`）。
- **头部字段集合 (Headers)**：以 `Key: Value` 形式排列的元数据。
- **空行 (CRLF)**：必须存在的回车换行，用于明确切分头部与正文。
- **消息正文 (Entity / Body)**：实际传输的数据实体。

### 三、 HTTP 核心传输机制与内容协商

#### 1. 实体数据类型与编码

- **MIME Type**：
  - `text`：文本数据（如 `text/html`、`text/plain`、`text/css`）。
  - `image`：图像文件（如 `image/gif`、`image/jpeg`、`image/png`、`image/webp`）。
  - `audio / video`：音视频流（如 `audio/mpeg`、`video/mp4`）。
  - `application`：复合或二进制数据（如 `application/json`、`application/javascript`；未知格式常标识为 `application/octet-stream`）。
- **Encoding Type（压缩格式）**：`gzip`、`deflate`、`br`（专门为 HTTP 优化的 Brotli 算法）。

#### 2. 内容协商字段及优先级计算

客户端通过请求头表达偏好，服务端通过响应头告知最终采用的规格：



| **协商维度** | **客户端请求头 (Accept)** | **服务端响应头 (Content)**                        |
| ------------ | ------------------------- | ------------------------------------------------- |
| **数据格式** | `Accept`                  | `Content-Type`                                    |
| **压缩编码** | `Accept-Encoding`         | `Content-Encoding`                                |
| **语言类型** | `Accept-Language`         | `Content-Language`                                |
| **字符集**   | `Accept-Charset`          | 并在 `Content-Type` 尾部通过 `; charset=xxx` 体现 |

- **权重因子（q 值）**：

  - 取值区间：`0.01 ~ 1.0`，默认值为 `1`，若为 `0` 则表示明确拒绝。

  - 语法规则：在类型后以分号追加 `;q=value`。

  - *示例*：`Accept: text/html, application/xml;q=0.9, */*;q=0.8`

    表示优先返回 HTML（权重 1.0），其次为 XML（权重 0.9），最后接受其他任意类型（权重 0.8）。

- **Vary 响应头**：告知中间代理服务器当前响应依赖的客户端协商头（如 `Vary: Accept-Encoding, User-Agent`），便于代理层对同一 URI 缓存不同版本的响应实体。

#### 3. 定长与不定长数据传输

- **定长数据**：
  - 显式指定 `Content-Length`，取值必须与实际发送字节数完全一致（过短会引发数据截断，过长会导致接收端等待超时）。
  - 若采用了 Gzip 压缩，`Content-Length` 表示压缩后的体积。
- **不定长数据（Chunked）**：
  - 在持久连接中，若数据无法预知总长，设置 `Transfer-Encoding: chunked`。
  - 数据以一系列分块流式发送，每个分块前附带当前分块十六进制长度，以长度为 0 的空分块作为终止标记。
  - 当存在 `Transfer-Encoding: chunked` 时，`Content-Length` 将被忽略。

### 四、 HTTP 请求方法与 GET / POST 深度对比

#### 1. 标准请求方法

- `GET`：请求获取 Request-URI 对应的资源（安全且幂等）。
- `POST`：向 Request-URI 附加新数据，产生业务副作用（非幂等）。
- `HEAD`：获取资源的响应报头，不返回响应正文（常用于检测资源元数据或有效性）。
- `PUT`：全量存储/替换指定的 Request-URI 资源（幂等）。
- `DELETE`：删除指定的 Request-URI 资源（幂等）。
- `OPTIONS`：询问服务器针对特定资源支持的请求方法；在 CORS 跨域通信中作为“预检请求（Preflighted）”嗅探权限。
- `TRACE`：回显服务器收到的请求信息，用于链路诊断。
- `CONNECT`：要求代理服务器建立隧道通信（通常用于代理 HTTPS 请求）。

#### 2. GET 与 POST 的核心差异

1. **语义与幂等性**：GET 具有幂等性（多次执行结果一致且无副作用）；POST 不具有幂等性。
2. **数据传输位置**：GET 参数拼装在 URL 查询字符串中，受浏览器及服务器 URL 长度限制；POST 数据存放在请求体（Body）中，无固定长度上限。
3. **缓存表现**：GET 请求可被浏览器主动缓存，可被保留在历史记录或加入书签；POST 默认不被缓存。
4. **编码能力**：GET 仅支持 ASCII 字符并执行 URL 编码；POST 支持多种媒体格式（如 `application/json`、`multipart/form-data`、二进制文件流）。
5. **底层网络包行为**：GET 报文通常包含在单个 TCP 包中发送；POST 很多时候在部分客户端实现中会拆解为两个阶段（先发 Headers，收到服务器 `100 Continue` 确认后再发送 Body）。

### 五、 HTTP/1.x 队头阻塞与持久连接

#### 1. 队头阻塞（Head-of-Line Blocking）

- **成因**：HTTP/1.1 开启 `Connection: keep-alive` 后共用一个 TCP 连接，但多个请求在应用层必须按串行顺序依次应答。若队首请求处理缓慢，后续所有请求都将被迫排队阻塞。
- **规避策略**：
  - **并发连接**：客户端针对同一域名建立多个独立的 TCP 连接通道（主流浏览器通常限制为 6 个并发连接）。
  - **域名分片（Domain Sharding）**：将静态资源分散部署到不同的二级域名（如 `img1.demo.com`、`img2.demo.com`），绕过单域名的并发连接上限。

#### 2. Connection: keep-alive（持久连接）

- **背景**：HTTP/1.0 默认为短连接，每次交互均需经历完整的三次握手与慢启动阶段；HTTP/1.1 默认开启 `Connection: keep-alive`。
- **优势**：重用 TCP 链路，大幅减少网络握手时延、降低 CPU 消耗并缓解网络拥塞。

### 六、 核心版本演进：从 HTTP/1.0 到 HTTP/3

| **特性维度**   | **HTTP/1.0**     | **HTTP/1.1**                 | **HTTP/2.0**                  | **HTTP/3**                   |
| -------------- | ---------------- | ---------------------------- | ----------------------------- | ---------------------------- |
| **底层协议**   | TCP              | TCP                          | TCP                           | **QUIC (基于 UDP)**          |
| **连接复用**   | 默认短连接       | 默认持久连接（存在队头阻塞） | 单连接**多路复用**            | 单连接多路复用（无连接阻塞） |
| **传输形式**   | 纯文本           | 纯文本                       | **二进制分帧**                | 二进制分帧                   |
| **头部处理**   | 每次完整发送明文 | 明文传输，冗余大             | **HPACK 静态/动态字典压缩**   | **QPACK 压缩**               |
| **服务器能力** | 仅被动响应       | 仅被动响应                   | **Server Push（服务端推送）** | Server Push                  |
| **队头阻塞**   | 存在             | 存在（应用层阻塞）           | 应用层解决，**TCP 层仍存在**  | **彻底解决（传输层无阻塞）** |
| **握手延迟**   | 1 RTT (TCP)      | 1 RTT (TCP)                  | 3~4 RTT (TCP + TLS)           | **0-RTT / 1-RTT**            |

#### HTTP/2 核心技术细节

- **二进制分帧**：将所有传输信息切割为二进制帧，拆分为存放头部的 `Headers 帧` 与存放正文的 `Data 帧`，机器解析无需状态机判断换行符，解析效率更高。
- **Stream ID 与多路复用**：
  - 同域名通信聚合在单个 TCP 连接上；
  - 数据帧携带 `Stream ID`，不同流之间的数据帧可以乱序交织发送；
  - 接收端根据 `Stream ID` 重新组合出各自完整的请求或响应报文，消除应用层队头阻塞。
- **HTTP/2 的局限性**：由于仍运行在 TCP 之上，一旦链路发生丢包，TCP 协议会触发重传机制并暂停滑动窗口，使得整条连接上的所有流均被挂起等待重传。

#### HTTP/3 与 QUIC 协议

- 基于 UDP 开发了传输层 **QUIC 协议**，在 UDP 之上自行实现流量控制、可靠重传与拥塞控制算法。
- 集成 **TLS 1.3**，连接建立与密钥协商合并完成（支持 0-RTT 极速建连）。
- 各个 Stream 独立拥有重传机制，单流丢包仅影响当前流，彻底根除 TCP 级队头阻塞。

### 七、 HTTPS 安全通信与加密机制

HTTPS 本质为 **HTTP + SSL/TLS + TCP/IP**，标准通信端口为 **443**。



#### 1. 加密技术组合

- **对称加密**：数据加密与解密使用相同的密钥，计算速度快，用于实际业务数据传输。
- **非对称加密**：公钥加密、私钥解密，用于身份认证及安全协商对称密钥。
- **散列函数（Hash）**：如 MD5、SHA 系列，用于生成信息摘要，验证数据完整性。
- **数字签名与证书体系**：
  - 解决“公钥防伪”问题：CA 权威机构使用自己的私钥对网站公钥及站点元数据签名生成证书。
  - 客户端使用内置受信任 CA 的公钥校验签名，确认证书真实可信，防止中间人伪造公钥。

#### 3. 会话恢复机制（SSL Session Resumption）

- **Session ID**：服务端在内存中维护会话编号与会话密钥映射，客户端重连时携带 Session ID。缺点是难以在集群反向代理场景下跨节点共享状态。
- **Session Ticket**：服务端加密会话信息后发给客户端存储，客户端重连时带回 Ticket，由服务端解密验证并复用密钥，天然支持分布式集群。

### 八、 浏览器缓存机制（强缓存与协商缓存）

Plaintext

```
发起请求 ──> 是否存在本地缓存？
                ├── 否 ──> 向服务器发起全新请求
                └── 是 ──> 强缓存是否命中 (Expires / Cache-Control: max-age)？
                             ├── 命中 (未过期) ──> 200 (from memory/disk cache)
                             └── 失效 (已过期) ──> 向服务器发起协商缓存校验
                                                     ├── Etag / Last-Modified 校验一致 ──> 304 Not Modified
                                                     └── 校验不一致 (资源已更新)       ──> 200 返回新资源
```

#### 1. 强缓存

- `Expires`：HTTP/1.0 产物，基于服务器绝对时间戳判定，受客户端本地时钟偏差影响。
- `Cache-Control: max-age`：HTTP/1.1 产物，指定相对有效时长（秒）。**优先级高于 Expires**。

#### 2. 协商缓存

- **修改时间方案**：
  - 响应头返回 `Last-Modified`；下次请求在 `If-Modified-Since` 中携带该时间戳。
  - *缺点*：以秒为最小粒度，秒级以内的变更无法检测；若文件仅周期性打开重存而内容未变，仍会导致缓存失效。
- **实体指纹方案**：
  - 响应头返回根据内容计算的 `ETag` 哈希；下次请求在 `If-None-Match` 中携带该标记。
  - **优先级高于 Last-Modified**，精确度更高。

### 九、 TCP 传输层原理深度剖析

#### 1. TCP 为什么需要三次握手？

TCP 核心标志位包含：`SYN`（同步）、`ACK`（确认）、`FIN`（终止）、`RST`（重置）。



- **握手步骤解析**：

  - **第一次握手**：客户端发送 `SYN`，服务端收到，服务端确认了“客户端发送能力正常、服务端接收能力正常”。
  - **第二次握手**：服务端回传 `SYN + ACK`，客户端收到，客户端确认了“双向收发均正常”，但此时服务端尚未确认客户端的接收能力是否就绪。
  - **第三次握手**：客户端回发 `ACK`，服务端收到，服务端最终确认“客户端接收能力正常”，双向连接就绪。

- **为什么两次握手不行？（防止失效历史报文导致资源浪费）**：

  若客户端发送的连接请求在网络中滞留，连接超时后客户端已关闭等待；若该滞留报文延迟到达服务端，服务端若仅凭两次握手就建立连接并保持资源等待，将造成服务端资源的空转与浪费。通过第三次握手，服务端在未收到客户端 ACK 确认前不会盲目维持连接。

- **握手阶段携带数据规则**：

  前两次握手禁止携带正文数据（防止伪造连接引发放大泛洪攻击）；第三次握手客户端已处于 `ESTABLISHED` 状态，允许携带正文数据。

#### 2. 为什么断开连接需要四次挥手？

- **挥手流程**：

  1. 客户端发送 `FIN` 报文，进入 `FIN_WAIT_1` 状态（表示客户端无新数据发送）。
  2. 服务端返回 `ACK` 报文，进入 `CLOSE_WAIT` 状态（确认收到关闭意图）。
  3. 服务端处理自身未发完的数据与释放资源，准备就绪后向客户端发送 `FIN` 报文，进入 `LAST_ACK` 状态。
  4. 客户端接收 `FIN` 后返回 `ACK` 报文，并进入 `TIME_WAIT` 等待 2MSL，服务端收到 ACK 后彻底关闭。

- **核心成因（全双工与非对称半关闭）**：

  TCP 通信为全双工通道。客户端发送 FIN 仅表明客户端单向不再发送数据，服务端此时可能仍有未处理完成的数据需要推送到客户端，因此服务端的 `ACK`（确认收到断开请求）和 `FIN`（自己也准备好关闭）无法合并为一次发送，必须分步执行。

### 十、 DNS 协议与网络代理机制

#### 1. DNS 查询原理

- **协议与端口**：运行于 **UDP 协议** 之上，使用 **53 端口**（避免 TCP 连接握手时延对海量小包查询造成迟滞）。
- **查询链路**：
  1. 浏览器缓存 -> 系统缓存 -> 本地 `hosts` 文件。
  2. 向本地 DNS 服务器（Local DNS）发起查询（**递归查询**：客户端只发一次请求，本地 DNS 负责返回最终 IP）。
  3. 本地 DNS 依次向根域名服务器、顶级域（.com）服务器、权威域名服务器层层查询（**迭代查询**：由本地 DNS 服务器多次发起下一级查询）。
- **DNS 负载均衡**：权威 DNS 在单个域名下配置多个服务节点 IP，通过轮询等算法动态打乱响应顺序，使客户端就近或均衡发起连接。

#### 2. 正向代理 vs 反向代理

- **正向代理 (Forward Proxy)**：
  - 代理对象是**客户端**，服务端感知不到真正发起请求的客户身份（常用于内网穿透、科学上网、访问加速）。
- **反向代理 (Reverse Proxy)**：
  - 代理对象是**服务器**，客户端以为访问的就是真实服务器，实际请求由反向代理统一接收并按照负载均衡策略（加权轮询、最小连接、IP Hash 等）分发给内部服务器集群。

### 十一、 实时通信演进：短轮询、长轮询与 WebSocket

#### 1. 传统通信弊端与轮询方案

- **短轮询 (Short Polling)**：客户端以固定时间间隔（如每 2 秒）发起 HTTP 请求询问状态。
  - *缺点*：若无数据更新会产生大量空请求，浪费带宽和服务器计算资源。
- **长轮询 (Long Polling)**：客户端发起 HTTP 请求后，若服务端无数据更新则将连接挂起，直至有新事件触发或连接超时才返回响应。
  - *缺点*：连接常态化挂起依然消耗连接资源，高并发场景下维护大量挂起 HTTP 请求的开销依然较高。

#### 2. WebSocket 全双工通信

- **诞生背景**：解决 HTTP 半双工通信与被动应答模式的缺陷，满足网络游戏、金融行情、即时通讯等高实时交互场景。

- **核心特征**：

  - **协议标识**：非加密为 `ws://`（默认端口 80），加密为 `wss://`（默认端口 443），能天然复用现有防火墙通行规则。
  - **数据格式**：基于轻量级二进制帧进行通信，帧头体积远小于 HTTP 头部；客户端向服务端发送数据强制包含掩码（Masking），服务端推流不需要掩码。

- **握手升级流程（借助 HTTP 协议升级通道）**：

  客户端发起特殊的标准 HTTP GET 请求：

  HTTP

  ```
  GET /chat HTTP/1.1
  Host: server.example.com
  Upgrade: websocket
  Connection: Upgrade
  Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
  Sec-WebSocket-Version: 13
  ```

  服务端响应 `101 Switching Protocols` 确认升级：

  HTTP

  ```
  HTTP/1.1 101 Switching Protocols
  Upgrade: websocket
  Connection: Upgrade
  Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
  ```

  完成握手后，连接脱离 HTTP 状态机，正式转入全双工二进制帧的双向实时通信模式。
